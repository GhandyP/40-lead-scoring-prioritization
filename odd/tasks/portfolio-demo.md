Implementation assumptions (not additional user requirements): use only Go's standard library; bind to localhost:8080; read-only fictional data; English technical artifacts. Scores are illustrative advisory rules, not calibrated conversion probabilities. No authentication, database, deployment or CRM actions. Replace the non-buildable cookbook helper rather than retain its behavior.
Integration contract: module github.com/GhandyP/40-lead-scoring-prioritization, Go 1.22. Domain exports Lead{ID,Name,Company string; RequestedDemo,BudgetConfirmed bool; TimelineDays,Interactions *int}, Score{Lead Lead; Score int; Band string; Reasons,Missing []string; Version string}, Rank([]Lead)([]Score,error), SampleLeads() []Lead. JSON uses snake_case. Rules v1: demo +30, confirmed budget +25, timeline <=30 days +25 (31–90 +10, otherwise 0), interactions min(n,4)*5. Scores 0–100; high >=70, medium >=40, low otherwise. Nil optional numbers are missing, not zero; negatives, blank IDs and duplicates return an error without modifying input. Ties use ID ascending. Fixtures use fictional people/companies; no protected or demographic attributes. Explain reasons and missing data, never fabricate confidence. Dashboard and /api/leads are GET-only, unknown routes 404, other methods 405 with Allow: GET. Search q and band filters apply to the dashboard; clear filters restores the dataset. NewHandler() http.Handler connects the UI to Rank(SampleLeads()). main starts localhost:8080. UI has labels, responsive layout, visible methodology and fictional/advisory disclaimer.
